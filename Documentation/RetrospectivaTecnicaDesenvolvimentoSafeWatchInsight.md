## 1. Finalidade e delimitação

Esta retrospectiva reconstrói a evolução técnica do Safe Watch Insight a partir do histórico Git, da documentação versionada e da implementação disponível. Seu propósito é fornecer material rastreável para discutir problema, requisitos, decisões, desenvolvimento incremental, validação e limitações. Não substitui a monografia, seu referencial teórico, os instrumentos de pesquisa ou a formatação exigida pela instituição.

A plataforma evoluiu de um frontend demonstrativo para um protótipo integrado de apoio a inspeções, auditorias e fiscalizações de Segurança e Saúde no Trabalho (SST). O fluxo principal utiliza autenticação, PostgreSQL/Neon, checklists versionados, snapshots por inspeção, respostas, não conformidades, ações corretivas, evidências fotográficas online, relatórios sob demanda e indicadores reais. O primeiro incremento offline permite executar inspeções previamente disponibilizadas no dispositivo, com persistência local e sincronização de respostas e conclusão.

A presença desse conjunto não demonstra prontidão comercial, conformidade legal integral, segurança completa ou correção sob qualquer concorrência. A [auditoria pré-escrita](./RelatorioAuditoriaTecnicaPreEscritaTCC.md), §§1, 3, 8 e 9, autorizou o avanço da escrita com o parecer **APPROVED WITH REQUIRED QUALIFICATIONS**. Permanecem cinco defeitos confirmados, cinco riscos potenciais e quatro limitações aceitas em seu inventário de 14 achados, além das ressalvas adicionais de dependências e reprodutibilidade. Nenhum desses 14 achados foi corrigido nesta retrospectiva.

O escopo desta entrega é exclusivamente documental. Código, dependências, lockfiles, schema, migrations, seeds, configuração de implantação e documentos preexistentes foram preservados. Não foram executadas operações de banco, instalação de dependências ou implantação. O relatório de auditoria foi apenas incorporado ao Git no checkpoint, sem edição de seu conteúdo.

### 2.3. Vocabulário da matriz

As classificações abaixo são cumulativas: uma funcionalidade pode estar implementada, possuir testes com resultado registrado e ainda apresentar limitações.

| Categoria                                                     | Critério utilizado                                                                                                                               |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Implementado** (_Implemented_)                              | Código atual sustenta a existência do mecanismo e seu caminho de execução                                                                        |
| **Testado automaticamente** (_Automated-tested_)              | Teste identificado e resultado de execução registrado; simples existência de script não basta                                                    |
| **Validado manualmente** (_Manually validated_)               | Registro explícito de conferência manual; leitura estática, E2E automatizado e roteiro de demonstração não são reclassificados como teste manual |
| **Verificado em implantação** (_Deployment-verified_)         | Registro de smoke check no domínio publicado ou status de deploy, restrito ao que foi observado                                                  |
| **Documentado, não verificado** (_Documented but unverified_) | Requisito, objetivo, roteiro ou declaração sem evidência suficiente para o resultado pretendido                                                  |
| **Limitação conhecida** (_Known limitation_)                  | Restrição, defeito, risco ou recurso incompleto/adiado, com a natureza detalhada separadamente                                                   |
| **Histórico** (_Historical_)                                  | Estado ou resultado de uma baseline anterior; não transferido automaticamente à atual                                                            |

“Homologação” designa o processo técnico registrado no projeto. Seu parecer não comprova avaliação por banca, aceitação por usuários finais, certificação externa ou ensaio formal de segurança. Não foi localizado um protocolo versionado que permita atribuir aprovação independente a esses atores. A homologação de setembro possui cenários automatizados e verificações de implantação registradas; não deve ser descrita integralmente como teste manual.

## 4. Arquitetura e tecnologias efetivamente utilizadas

### 4.1. Aplicação integrada e stack

Frontend, renderização no servidor e Server Functions pertencem ao mesmo projeto TanStack Start. Nitro gera o artefato para Vercel; o banco é PostgreSQL, com uso de Neon documentado nas integrações. Não há backend REST separado nem implementação de Express, Fastify ou NestJS. O título [Especificação API REST](./EspecificacaoAPIREST.md) é uma denominação acadêmica preservada; os contratos reais são Server Functions.

| Framework/rotas           | `@tanstack/react-start` 1.168.60, `react-router` 1.170.41, `router-plugin` 1.168.42                   |
| Transporte servidor       | `@tanstack/start-server-core` 1.169.39                                                                |
| Estado remoto/formulários | React Query 5.101.2; React Hook Form e resolvers Zod                                                  |
| Validação                 | Zod da raiz 3.25.76; não confundir versões aninhadas de ferramentas com schemas da aplicação          |

### 4.2. Camadas e desvios da convenção

A convenção de `AGENTS.md` é:

```text
Tela → React Query → Server Function/API → Service → Repository → Prisma → PostgreSQL
```

O caminho é observável, por exemplo, em [useCompanies](../src/hooks/useCompanies.ts), [company.functions](../src/lib/api/company.functions.ts), [CompanyService](../src/server/services/company.service.ts) e [CompanyRepository](../src/server/repositories/company.repository.ts). Hooks administram consultas, mutações e invalidações; Functions validam entrada e sessão; Services coordenam regras; Repositories encapsulam Prisma e persistência.

Entretanto, a implementação não aplica literalmente todas as simplificações da convenção:

| Convenção ou expectativa                    | Implementação observada e implicação                                                                                                                                 |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Toda tela passa por React Query             | Login chama a Function diretamente; o guard `beforeLoad` consulta `getAppSession` antes da renderização. Cadastro usa mutation e React Hook Form                     |
| Toda resposta vai imediatamente ao servidor | Respostas e conclusão passam primeiro por Dexie/fila, mesmo online; o sincronizador chama a Function depois                                                          |
| Toda regra está exclusivamente no Service   | Schemas validam contratos; helpers calculam hashes; Repositories também aplicam ownership, revisão, deduplicação e transações; SQL impõe invariantes estruturais     |
| Repository apenas executa escrita simples   | Na cópia, a transação lê origem/títulos e chama callback síncrono do Service para preparar conteúdo dentro da mesma leitura transacional                             |
| Todas as entidades possuem CRUD web         | `Report`, modelos legados, metadados de sincronização e estruturas de snapshot não têm CRUD universal exposto; `getGreeting` é exemplo sem persistência SST          |
| Toda consulta é isenta de escrita           | Dashboard/relatório derivam atrasos; consultas específicas de NC/ações podem executar `markOverdue` e persistir status                                               |
| Todo erro tem envelope uniforme             | Validators anteriores ao handler e exceções inesperadas podem lançar fora de `Result`; `statusCode` do resultado é lógico, não promessa do status HTTP do transporte |

Essas diferenças estão descritas em [AI/Architecture](../AI/Architecture.md) e foram confrontadas com os arquivos citados. Nenhuma tela inspecionada consulta Prisma diretamente. Imports de tipos ou enums gerados não equivalem a abrir conexão com o banco. Seeds e validadores operacionais ficam fora da fronteira web e podem utilizar Prisma diretamente.

### 4.3. Frontend, roteamento e erros

O roteamento por arquivos em [src/routes](../src/routes/) gera `routeTree.gen.ts`. `__root.tsx` organiza providers e boundary de erro; `_app.tsx` protege a navegação e usa `AppShell`. `src/router.tsx` cria um `QueryClient` por router. A revisão documental final inventariou 16 destinos, incluindo `/`, e 15 telas; não se traduz essa contagem em cobertura E2E.

As query keys ficam em `src/lib/api/*.query-keys.ts`. As mutations verificam `result.success` antes de invalidar caches, pois um resultado de negócio malsucedido pode chegar a `onSuccess` do React Query. O padrão de resposta tem `success`, `data` em sucesso e `message`, `code`, `statusCode`, eventualmente `errors`, em falha. Não existe campo universal `error` nem conversão garantida de toda exceção. A classificação genérica de erros pelo sincronizador é um defeito mantido na seção 11.

TypeScript está em modo estrito no [tsconfig](../tsconfig.json). Seu `include` cobre `src` e configurações específicas, sem abranger automaticamente todos os scripts e E2E. Aprovação do typecheck oficial não prova aprovação de uma configuração ampliada.

### 4.4. Persistência e evolução do modelo

O [cliente Prisma](../src/server/prisma/client.ts) utiliza `PrismaPg`, `DATABASE_URL` e reuso global fora de produção. O client é gerado em `src/generated/prisma`; a configuração de migrations está em [prisma.config.ts](../prisma.config.ts). Modelos e migrations devem ser lidos conjuntamente: índices parciais e CHECKs não estão integralmente representados pelo schema.

| Migration                                                        | Transformação principal                                                                                                |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `20260705165125_init`                                            | Modelo inicial de usuários, empresas, checklists/itens/normas, inspeções/respostas, NCs/ações, evidências e relatórios |
| `20260725180000_add_corrective_action_5w2h`                      | Campos de planejamento 5W2H nas ações corretivas                                                                       |
| `20260803150000_add_checklist_versions_and_inspection_snapshots` | Versões, itens/normas versionados, snapshots/itens/normas históricos, compatibilidade e backfill                       |
| `20260806120000_complete_evidence_mvp`                           | Metadados necessários ao MVP de evidências e seu vínculo contextual                                                    |
| `20260806220000_add_offline_sync_idempotency`                    | Registro persistido de operações offline e horário original do cliente                                                 |
| `20261003000000_add_official_checklist_templates`                | Oficialidade, autoria nullable institucional e constraints correspondentes                                             |

O modelo atual tem 19 models e 12 enums. O dicionário e as Fases 10–11 registram 36 FKs, 19 PKs, 74 índices explícitos e 13 CHECKs no DDL consolidado. Esses últimos números são resultados históricos da conferência estrutural, não nova introspecção do Neon. A Fase 10 corrige a contagem de índices do relatório anterior; deve-se usar a errata, preservando o registro original.

Soft delete existe em entidades específicas, sem liberar automaticamente UNIQUE ou FKs. `DateTime` corresponde a `TIMESTAMP(3)` nas migrations, e UUID/defaults gerados pelo Prisma não devem ser confundidos com defaults SQL universais. `ChecklistItem` e sua associação normativa continuam como legado; a edição atual usa itens de versão. A divergência referencial de `Checklist.createdById` é mantida na seção 11. Não houve inspeção de drift remoto nesta retrospectiva.

### 5.2. Versionamento, execução e alcance do histórico

`Checklist` representa identidade e catálogo; `ChecklistVersion` contém conteúdo editorial nos estados `DRAFT`, `PUBLISHED` e `RETIRED`. A publicação calcula SHA-256 canônico e registra autoria/data/formato. A edição posterior deriva draft; publicações e versões retiradas não são editadas pelos fluxos normais. O banco restringe um draft por checklist e o número de versão, mas não executa uma assinatura digital do documento.

Na criação, [InspectionService](../src/server/services/inspection.service.ts) verifica empresa própria, checklist acessível/ativo e versão publicada. [InspectionRepository](../src/server/repositories/inspection.repository.ts) grava inspeção e snapshot conjuntamente. A preparação e algumas verificações precedem a transação: não se afirma atomicidade universal entre toda leitura de elegibilidade e qualquer alteração concorrente.

O snapshot conserva título, descrição, versão de origem, itens, ordem, obrigatoriedade e cópias normativas. Respostas apontam ao item histórico; o Service mantém compatibilidade para mapear identificadores legados. `NON_COMPLIANT` assegura NC; outras respostas arquivam a NC ativa. A primeira resposta pode iniciar a inspeção; a conclusão exige os itens obrigatórios respondidos. `NOT_APPLICABLE` conta como resposta e itens opcionais podem permanecer sem resposta.

Novas respostas são bloqueadas em `COMPLETED`/`CANCELLED`, ressalvado o caminho de retry idempotente de operação já aplicada. NCs, ações e evidências podem continuar sendo tratadas após conclusão. O snapshot não congela empresa, inspetor, todos os eventos ou todo o relatório. O backfill antigo é não verificável; além disso, o rótulo `VERIFIED` em novas inspeções sobre formatos antigos possui o defeito IC-P9-04. Portanto, “histórico do conteúdo do checklist” é uma alegação sustentada; “histórico integral inviolável e universalmente verificado” não é.

### 5.3. Templates, cópia e dataset demonstrativo

O catálogo institucional tem dois templates: construção, com 12 itens e NR-18; trabalho em altura, com oito itens relacionados a NR-1, NR-6 e NR-35. A oficialidade é da plataforma, não uma chancela governamental. `isOfficial` é distinto de `isTemplate`; autoria institucional usa proprietário `NULL` e restrições próprias. O bootstrap é explícito em [seed-platform.ts](../prisma/seed-platform.ts), independente da conta demo e não executado automaticamente na inicialização.

[ChecklistService](../src/server/services/checklist.service.ts) seleciona draft próprio ou publicação elegível conforme o leitor. Terceiros não copiam draft privado. A cópia cria identidade pessoal, draft v1, itens e associações próprios, sem transferir inspeções, respostas ou evidências. A linhagem por item preserva ancestral publicado; cópia de draft não cria dependência ao item mutável da origem. A publicação usada como origem exige formato 1 e hash íntegro. A transação `RepeatableRead` e os inserts em lote estão em [ChecklistRepository](../src/server/repositories/checklist.repository.ts). A convenção “— Cópia”, “— Cópia (2)” não assegura exclusividade concorrente de títulos.

O [Demo Seed](../prisma/seed.ts) usa IDs determinísticos, marcador sintético e verificações de colisão/atividade. Utiliza Services em fluxos de domínio e Prisma em preparação/verificação. Não apaga indiscriminadamente dados existentes e não reinicializa automaticamente uma conta incompatível. O README prevê upload real de fotografias durante a demonstração; não há imagens fictícias apresentadas como evidência operacional já enviada.

### 5.4. Relatórios, indicadores e evidências

[ReportRepository](../src/server/repositories/report.repository.ts) consulta a inspeção própria e seu snapshot. A lista de relatórios disponíveis exige conclusão; o detalhe por ID exige ownership/snapshot e pode representar inspeção parcial. [InspectionReport](../src/components/reports/InspectionReport.tsx) apresenta conteúdo e usa impressão/CSS A4; a visualização não cria um registro `Report`. Dados atuais de empresa/inspetor e tratativas devem ser diferenciados do checklist congelado.

O [DashboardService](../src/server/services/dashboard.service.ts) calcula conformidade como proporção de respostas `COMPLIANT` entre `COMPLIANT` e `NON_COMPLIANT` de inspeções concluídas com itens históricos. Exclui N/A e respostas legadas sem `snapshotItemId`; sem respostas aplicáveis, o percentual é `null`. Não é medida de cumprimento integral da legislação. ## 6. Segurança, autenticação e autorização

### 6.1. Evolução dos controles

Autenticação real foi incorporada em julho; o [helper de senha](../src/server/auth/password.ts) usa bcrypt com custo 12. O cadastro de setembro normaliza e-mail, exige senha de pelo menos oito caracteres e confirmação igual, rejeita extras e atribui `TECHNICIAN` no servidor. O resultado do cadastro não abre sessão: encaminha ao login. A consulta de duplicidade é insensível à caixa na aplicação; isso não transforma o índice SQL de e-mail em índice case-insensitive.

A [sessão](../src/server/auth/session.ts) usa cookie `safe_watch_session`, duração de oito horas, `HttpOnly`, `SameSite=lax`, `Path=/` e `Secure` em produção. O segredo é obrigatório em produção; a identidade é reconsultada como usuário não excluído. Não há JWT, Neon Auth ou tabela própria de sessões no fluxo atual. O [start.ts](../src/start.ts) configura middleware CSRF para Server Functions, introduzido no incremento E2E de agosto.

O hardening de evidências em 4 de setembro e o hardening do fluxo principal em 27 de setembro propagam a identidade confiável da sessão até Services/Repositories. Empresa usa `createdById`; checklist pessoal usa proprietário e `isOfficial=false`; inspeção usa `userId`; NC, ação e evidência herdam o contexto da inspeção. A proteção é repetida em consultas/mutações, não apenas em botões ou guard de rota. Recursos privados alheios e inexistentes normalmente têm a mesma resposta lógica `NOT_FOUND`.

Publicações acessíveis podem ser consultadas e reutilizadas sem compartilhar inspeções ou drafts privados. A marca `ADMIN` armazenada não implementa administração global; nem esse papel autoriza mutações institucionais pela API pessoal. Os testes de autorização e os validadores com dois usuários fornecem evidência direcionada, não um pentest universal.

O histórico também registra a remoção de `.env` do rastreamento em `e0790a7` e a atualização de `.gitignore` em `5ff5290`, em 5 de julho. A mensagem do commit indica preocupação com informação sensível, mas remoção do arquivo não demonstra rotação de credenciais nem eliminação de conteúdo do histórico. Não se acessaram ou reproduziram segredos antigos nesta investigação.

## 7. PWA, persistência offline e sincronização

### 7.1. Escopo implementado

O caminho offline complementa a arquitetura online:

```text
Tela/hook → pacote e operação em transação Dexie → fila local durável
    → sincronizador com aplicação ativa → Server Function autenticada
    → Service → Repository → mutação e confirmação no PostgreSQL
    → confirmação local e atualização dos indicadores
```

[database.ts](../src/offline/database.ts) define banco local versão 1 com sessão, pacotes de inspeção e operações. Os pacotes contêm inspeções já abertas/listadas online, com snapshot, itens, normas e respostas; não são uma cópia arbitrária de todo o cache React Query. O registro de resposta/conclusão é local primeiro, inclusive com rede disponível. A projeção de NC no pacote permite continuidade da execução, sem oferecer CRUD offline autônomo de todas as tratativas.

Cada operação possui UUID estável, sequência FIFO por usuário, payload e dependências. A recuperação de `SYNCING` conserva sua identidade. [sync-manager.ts](../src/offline/sync-manager.ts) aplica retry exponencial, no máximo cinco tentativas automáticas e teto configurado de cinco minutos para o intervalo. `409` bloqueia como `CONFLICT`; `401`/`422` retornados ficam em `ERROR`; exceções lançadas são genericamente classificadas como `NETWORK_ERROR`. A sincronização depende da aplicação ativa e de conectividade, sem Background Sync com navegador encerrado.

No servidor, identidade/hash e mutação são registrados na mesma transação em `OfflineSyncOperation`. Retry sequencial com mesmo UUID e identidade/payload compatíveis é deduplicado; reutilização divergente é rejeitada. A revisão de resposta usa `updatedAt` do servidor; `clientUpdatedAt` preserva horário do dispositivo. O protocolo não escolhe intencionalmente a última escrita como solução de conflito, mas sua comparação antes do upsert não assegura prevenção de toda corrida simultânea.

### 7.2. Worker, sessão local e três caches distintos

O [manifest](../public/manifest.json) configura `standalone`, início em `/inspecoes` e escopo `/`. O [worker](../public/sw.js) mantém caches de assets e navegação, pré-carrega fallback/manifest/ícone, remove versões antigas e controla clientes. Navegação é network-first; assets são cache-first, com tratamento network-first para módulos Vite. Não armazena POST, requisições de outra origem ou respostas de Server Functions como uma API cacheada.

É necessário separar três mecanismos: React Query guarda estado remoto em memória; IndexedDB guarda pacotes/fila/sessão segura local; Cache Storage guarda HTML e assets. A limpeza de um não prova limpeza dos demais. HTML autenticado pode entrar no cache de navegação, sem chave explícita por usuário nem expiração equivalente à sessão.

A sessão local guarda dados seguros do usuário por oito horas, sem senha ou conteúdo do cookie HttpOnly. Troca de identidade e logout limpam dados offline pelos caminhos implementados; a expiração local isolada não limpa todo o cache HTML. Sessão cacheada não autoriza mutação remota, não renova o cookie no servidor e não protege dados de quem controla o perfil do navegador/sistema operacional. Permanecem riscos de cache React Query, retenção HTML e falhas de limpeza.

Para IC-P6-03, idempotência e revisão são controles diferentes. A chave única de operação pode impedir duas confirmações persistidas iguais, sem assegurar resposta idempotente adequada a duas transações simultâneas. A conclusão tem atualização condicional de status, mas sua completude é verificada antes no Service; não há prova de atomicidade global entre salvar, verificar completude e concluir concorrentemente. O cenário de conflito homologado aplica uma mudança remota e depois sincroniza revisão antiga; não é corrida simultânea pela mesma revisão.

### 11.3. Priorização e fronteiras de escopo
